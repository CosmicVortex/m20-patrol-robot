## 一、问题验证结果

### P0-1: 健康检查逻辑过于严格 ✅ 确认存在

**位置**: `backend/app/api/handlers.py:72-74`

```python
and health["frame_valid"] is True      # telemetry.py:394 - valid_frames > 0
and health["message_parsed"] is True   # telemetry.py:395 - message_count > 0  
and health["status_accepted"] is True  # telemetry.py:396 - source=="REAL" and connected
```

**验证结论**: 问题真实存在。这些字段依赖数据流状态，在以下场景可能为False：
- 刚启动还未收到有效帧时
- 模拟模式下 `source != "REAL"`
- 连接断开后重连间隙

**风险评估**: 高。可能导致监控工具误判服务不健康，触发不必要的重启或告警。

**修复方案评估**: ✅ 合理
- 建议移除内部状态检查，只保留 `connected`、`source`、`valid_frames`、`bytes_received`
- 这些核心指标已足够判断连接健康状态

### P0-2: 运动控制默认授权 ✅ 确认存在

**位置**: `backend/app/motion/service.py:84-85`

```python
self._authorized: bool = True
self._authorized_by: str = "system"
```

**验证结论**: 问题真实存在。服务初始化即自动授权，任何用户无需Web UI显式授权即可发送控制指令。

**风险评估**: 高。安全风险：
- 如果`auth_enabled=false`且`allow_anonymous=true`（readonly-manifest.json实际配置），匿名请求可直接控制机器人
- 运动控制属于安全关键操作，必须显式授权

**修复方案评估**: ⚠️ 需谨慎
- 建议改为`authorized=False`是合理的生产配置
- **但会破坏现有测试**: `test_motion_state_switch_success`和`test_send_navigation_requires_authorization`依赖默认授权
- **建议**: 添加`--dev-mode`参数或通过环境变量`M20_DEV_MODE`控制默认授权行为，测试中使用dev模式

### P1-2: telemetry字段名不一致 ✅ 部分确认

**位置**: `backend/app/config.py:107`

```python
telemetry_tx_enabled=env_bool(
    "M20_TELEMETRY_TX_ENABLED", 
    data.get("telemetry_tx_enabled", False)  # 默认False
)
```

**验证结论**: 问题描述不够准确。
- manifest.json中实际包含`"telemetry_tx_enabled": true`，配置会正确加载
- 问题在于：如果用户使用旧版manifest只含`telemetry_rx_enabled`，tx配置会是False

**风险评估**: 低。当前manifest配置正确，不影响运行。

**修复方案评估**: ✅ 合理
- 添加`data.get("telemetry_rx_enabled", False)`作为后备是防御性编程
- 但建议明确这两个字段的语义差异：tx是心跳发送，rx是数据接收

## 二、遗漏问题发现

### 发现1: P1-3心跳发送顺序问题 ⚠️ 确认存在

**位置**: `backend/app/robot/telemetry.py:219-221`

```python
time.sleep(self.config.heartbeat_interval_s / 2)  # 0.5s
client.send_heartbeat_only()  # 在sleep后发送
```

**问题**: 如果`receive_messages`阻塞接近timeout（0.5s），加上sleep的0.5s，两次心跳间隔可能达到1s。虽然不超过2s阈值，但在网络抖动时风险增加。

**建议修复**: 先发送心跳再接收，确保固定间隔。

---

### 发现2: 测试命名误导 ⚠️ 需要修正

**位置**: `backend/tests/test_navigation_service.py:15`

```python
def test_initial_state_not_authorized(self):
    """Service starts auto-authorized in dev mode."""
    ...
    assert service.is_authorized == True  # 实际验证的是授权状态
```

**问题**: 测试名称与断言内容矛盾。名称说"not_authorized"，但断言验证"authorized=True"。

**建议**: 重命名为`test_initial_state_auto_authorized_in_dev_mode`

---

### 发现3: 安全配置与测试模式混淆 ⚠️ 潜在风险

**位置**: `deploy/readonly-manifest.json:14-15`

```json
"auth_enabled": false,
"allow_anonymous": true
```

**问题**: 生产manifest禁用了认证且允许匿名访问，而运动/导航服务默认授权。这意味着：
- 任何人都可以直接发送控制命令
- 除非部署在防火墙后的内网，否则存在严重安全风险

**建议**: 
1. 生产环境必须启用`auth_enabled: true`
2. 或者将运动/导航默认授权改为False
